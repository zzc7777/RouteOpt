>
> 最后更新：2026-10-05
>
> 语义依据：`reference/docs/模型和推导/DVRP 数学模型-v4.md`

本文只确定 M1 的上层结构、模块接口和正确性边界。它不是实现说明；文中对象名是逻辑名称，最终 C++ 类名可在实现时调整。

## 1. 目标与非目标

M1 要形成以下最小闭环：

```text
DVRP 八字段实例
  -> 动态事件与车辆状态
  -> 多起点静态阶段问题
  -> 标准 Branch-and-Price
  -> 阶段整数路线
  -> 推进到下一事件
  -> 累计实际执行距离
```

M1 先保证 2--5 个客户的手工实例语义正确，不追求 Solomon 100 客户性能。现有 CVRP/VRPTW 入口和默认流程不得改变。

## 2. 总体分层

| 层 | 职责 | 输入 | 输出 |
| --- | --- | --- | --- |
| 输入层 | 读取八字段 TXT | 文件路径 | 静态客户与披露时间 |
| 动态层 | 推进事件、车辆和承诺任务 | 上一阶段路线、当前时间 | 当前阶段快照 |
| 阶段构建层 | 把快照翻译为静态多起点 VRPTW | 阶段快照 | `StageProblem` |
| 阶段 BP 层 | RMP、pricing、加列和分支 | `StageProblem` | `StageSolution` |
| 仿真控制层 | 循环求解并累计已执行距离 | 全局问题 | 最终 DVRP 结果与日志 |

动态层不直接操作 LP、bucket 或 `BbNode`；阶段 BP 层也不决定客户何时披露、车辆当前承诺是否完成。

```python
state = create_initial_state(problem_data)

for event_time in disclosure_events:
    state = advance_previous_plan(state, event_time)
    state = release_customers(state, event_time)
    stage_problem = build_stage_problem(state)
    stage_solution = solve_stage_by_branch_and_price(stage_problem)
    state = accept_new_plan(state, stage_solution)

return finish_and_report_actual_distance(state)
```

## 3. 模块之间的数据契约

### 3.1 `StageProblem`

一次阶段求解只接收当前时刻的不可变快照：

```text
currentTime       当前事件时间 tau
inputData         对已有 reader 数据的只读访问，不要求新增 ProblemData 类
customers         本阶段必须覆盖的客户
originStart       不限车辆数量的原始起点
externalStarts    执行中车辆各自的专属外部起点
returnDepot       语义独立的共同返回节点
returnDeadline    最晚返场时间 H，来自车场行 DUE_DATE
fixedCostAfterTau 不参与路线选择、但需要报告的固定剩余成本
```

### 3.2 `StartSpec`

每个起点至少携带：

```text
startKey           阶段内稳定且唯一的起点标识
kind               ORIGIN 或 EXTERNAL
locationCustomerId 外部起点对应承诺客户；原始起点对应原车场
startTime         原始起点按允许的最早时刻 tau 发车；外部起点为 T^k
remainingCapacity 原始起点为 Q；外部起点为 R^k
```

外部起点位于承诺客户的逻辑副本，不把该承诺客户再次放入覆盖集合。共同返回节点必须和所有出发起点保持语义分离。
原始车场选中路线按允许的最早时刻发车，可以提前到达客户处等待；外部车辆按 v4 在 `T^k` 完成承诺后立即出发。刚好在事件时刻完成服务时，为同一辆车生成本阶段外部起点，保留已占用容量，先重优化，再于同一时刻出发。

### 3.3 `StageRoute`

现有 `SequenceInfo` 只有客户序列，无法区分多起点。DVRP 路线至少需要：

```text
startKey          从哪个原始/外部起点出发
customerSequence 本阶段访问的客户序列
travelCost        从该起点出发并回到 returnDepot 的成本
schedule          验证和状态推进所需的到达/服务时间
```

### 3.4 `StageSolution`

阶段结果至少包含求解状态、选中路线、可优化路线成本、固定剩余成本和 BP 统计。仿真控制层根据路线时间轨迹推进车辆，而不是从 LP 内部对象反推动态状态。
不可行、超时无可行解和超时已有可行解必须区分，不能只用一个成功标志覆盖全部状态。已确认超时即停止仿真，即使有可行整数解也不继续；保留已有解用于诊断，不能报告为证明不可行或仿真完成。

### 3.5 当前动态模块的文件与接入方案（待审阅）

本功能先做到状态推进、阶段输入生成和结果接收，以手工路线测试；阶段 BP 后续接入。建议新增 3 个生产文件（2 个 `.hpp`、1 个 `.cpp`），集中在 `packages_dvrp/application/dvrp/src/dynamic/`：

| 相对路径 | 职责 |
| --- | --- |
| `include/dynamic_data.hpp` | 定义车辆状态、`DynamicState`、`StageProblem`、起点和阶段路线结果等纯数据类型 |
| `include/dynamic_controller.hpp` | 声明初始化、推进到指定时间、生成阶段问题和接收计划的方法 |
| `src/dynamic_controller.cpp` | 实现上述方法，包含事件排序、距离结算和外部起点生成，不调用 LP 或标签算法 |

另加 `test/dynamic_test.cpp` 并更新 DVRP CMake 注册测试；本步不把 `main.cpp` 改成已经支持完整 BP。现有 reader 接口保留，不新增 `problem_data.hpp`；概念上的基础数据继续来自 `info_vertex`、容量等输入。求解失败只用手工结果测试接收边界，不实现 solver 的真实计时和中止机制；超时与仿真停止的联动留到阶段求解器接入时验证。

稳定的数据边界为：

```text
reader 输出（仿真期间保持有效、只读）
  -> DynamicController 持有并推进实际状态
  -> StageProblem（本阶段固定快照）
  -> StageSolver（后续）
       -> 编号和数组转换 -> 根 RMP / pricing 初始化
       -> LP 对偶值 + 当前节点分支限制 -> 定价与加列、搜索树
  -> StageSolution（带起点身份的整数路线和时间轨迹）
  -> DynamicController 校验并接续执行
```

动态控制器拥有实际状态和执行计划；阶段快照保存当时的客户与起点值，不能随下一事件改变。阶段求解器拥有其数组和 solver/tree 工作区，返回路线结果后不把内部对象交给动态层。仅转换输入不能消除原有单车场假设，RMP、标签起终点和加列仍须分别适配。

具体方法签名和独立验收例子在需求边界确认后补齐，按 `AGENTS.md` 的“代码架构与接口”步骤展示；以上是文件布局建议，不代表接口已实现。

### 3.6 平行源码树（目录隔离已确认，算法适配待实现）

用户已选择维护独立的 `packages_dvrp`，与原 `packages` 平行；后续按模块复制原代码，再在 DVRP 副本中适配，不直接修改原版。该选择替代此前“优先直接复用原公共模块”的目录方案。

```text

packages_dvrp/

  common/config/                 仅复制 reader 必需的 route_opt_macro.hpp
  branching/                     空目录，后续承载分支公共机制的独立副本
  deluxing/                      空目录

  rank1_cuts/                    空目录
  rounded_cap_cuts/              空目录
```

本次仅迁移已有功能，不批量复制求解算法；空目录不代表功能已实现或已启用。应用内的 `dynamic`、`stage_solver`、`node`、`pricing`、`add_column` 等仍按功能逐项设计。动态层只与阶段求解入口交换 `StageProblem` / `StageSolution`，不直接访问根节点、标签或分支内部对象。

复制时仍应分清源码职责：原 `packages/branching/bbt` 管理搜索树，静态应用的具体边流量统计及子节点约束位于 `application/cvrp/src/main`。DVRP 副本需要分别适配，不能仅移动目录或替换类型就宣称兼容多起点。

两套应用独立构建，DVRP 的源文件和头文件路径指向 `packages_dvrp`，不得把两套同名实现混入一个目标。复制保留许可证与来源；原版后续修复不会自动同步到副本。当前 reader 没有 solver 依赖；外部 solver/第三方依赖的接入方式留到对应模块确认。

## 4. 阶段 RMP 设计

令 `lambda[s,r]` 表示从起点 `s` 使用可行路线 `r` 的变量。

### 4.1 客户覆盖行

每个本阶段客户恰好服务一次：

$$
\sum_s\sum_{r\in\mathcal R_s} a_{ir}\lambda_{sr}=1.
$$

### 4.2 外部起点行

每个外部起点对应一辆已经在执行任务的具体车辆，因此恰好选择一条后续路线：

$$
\sum_{r\in\mathcal R_k}\lambda_{kr}=1.
$$

外部起点允许“直接返回共同车场”的空客户路线，以表达不再接新客户；该路线也必须满足最晚返场时间 `H`，不能无条件作为可行列加入。

### 4.3 原始起点

原始起点代表不限数量的待命车辆，不建立现有 RouteOpt 的车辆数行。原始起点普通路线必须至少访问一个客户，避免产生无意义的空路线变量。

### 4.4 根 RMP 与 Phase-I

根模型先加入：

- 每个外部起点的一条通过返场时间检查的直接返场列（若可行）；
- 已知可行的单客户路线；
- 为等式行准备的高惩罚人工变量。

人工变量只用于让初始 RMP 可求解并产生 dual。只有所有人工变量最终为 0，阶段问题才可报告为真实可行。

## 5. Pricing 设计

### 5.1 M1 采用逐起点调用

M1 不先构造带超级源点的统一图，而是复用一套 pricing 引擎，对每个起点建立一个上下文并分别调用：

```python
for start in stage_problem.all_starts:
    context = PricingContext(
        start=start,
        customers=stage_problem.customers,
        return_depot=stage_problem.return_depot,
        branch_constraints=constraints_for(start.startKey),
    )
    new_routes += exact_bucket_labeling(context, duals)
```

这样可以明确传入每个起点自己的初始时间、剩余容量和分支约束，也较容易隔离 RouteOpt 的单车场假设。客户之间的距离和资源数据可以共享，但起始弧、初始标签和分支上下文不能混用。

### 5.2 Reduced cost

客户覆盖行 dual 记为 `pi[i]`，外部起点行 dual 记为 `mu[k]`：

```text
原始起点路线：c(r) - sum(pi[i] * a[i,r])
外部起点路线：c(r) - sum(pi[i] * a[i,r]) - mu[k]
```

原始起点没有车辆数 dual，也没有外部起点 dual。

### 5.3 标签资源

标签扩展继续保留 RouteOpt 的 bucket graph 和 exact labeling。不同起点的初始化为：

| 起点 | 初始时间 | 初始可用容量 | 终点 |
| --- | --- | --- | --- |
| 原始起点 | `tau` | `Q` | `returnDepot` |
| 外部起点 `k` | `T^k` | `R^k` | `returnDepot` |

原始起点按允许的最早时刻 `tau` 实际发车，允许提前到达客户处等待。全部路线（含外部起点直接返场）须在 `returnDeadline = H` 前返回；成本、旅行时间及可行性容差按当前 RouteOpt VRPTW 口径，与动态结算一致。

M1 小实例优先使用完整客户访问记忆，以保证 elementary exact pricing；动态 ng/DSSR 暂时关闭。若未来扩展到大实例，再单独验证 ng-route 松弛、增强和停止证明。

## 6. Add-column 与列生命周期

pricing 输出不能再只是客户序列，而应输出带 `startKey` 的候选路线。加列模块据此：

1. 从指定起点计算首弧；
2. 从最后一个客户连接独立 `returnDepot`；
3. 填写客户覆盖行；
4. 仅对对应外部起点行填写系数 1；
5. 原始起点列不填写车辆数行；
6. 用真实 RMP 系数复核 reduced cost 后加入 Solver 和当前节点列池。

Solver 变量顺序和路线对象顺序仍必须一一对应。

## 7. Branching 设计

M1 建议先使用“起点专属有向弧流量”：

$$
x^s_{ij}=\sum_{r\in\mathcal R_s}a^r_{ij}\lambda_{sr}.
$$

它与当前 RouteOpt 的无向聚合边 `q[{i,j}]` 不同：

- 保留 `i -> j` 的时间方向；
- 不把不同外部车辆或原始起点的流量混在一起；
- 起点到首客户、客户间弧和客户到返回节点都可使用同一分支键 `(startKey, i, j)`。

选择一个分数弧后生成：

```text
左分支：x^s_ij = 0
右分支：x^s_ij = 1
```

左分支只删除并禁止该 `startKey` 上使用该有向弧的列；右分支增加一条等式，其 dual 也只修改该起点的 pricing 上下文。不能从共享图中把其他起点的同名弧一并删除。

该选择比直接复用无向 `q_ij` 更容易保持多起点分配语义，但仍需用枚举小实例验证：只要 LP 路线变量分数，就一定能找到有效的分数弧候选。若反例存在，再增加兼容列生成的 fallback branching，不能把分数解误报为整数解。

## 8. 动态阶段与 Solver 生命周期

每个事件时刻都必须从新的 `StageProblem` 重建根 RMP、pricing 上下文和搜索树：

```text
事件 tau_1 的 BbNode / 列 / dual / 分支约束
    不得复用到
事件 tau_2 的阶段模型
```

原因是客户集合、外部起点数量、起点时间、剩余容量和主问题行都会变化。阶段内父子 `BbNode` 可以按 Branch-and-Price 正常继承状态；跨阶段禁止继承 Solver 模型。

## 9. M1 功能配置

| 类别 | M1 状态 | 原因 |
| --- | --- | --- |
| RMP、加列、基础搜索树 | 保留 | 标准 BP 核心 |
| bucket graph、exact labeling | 保留 | 当前 RouteOpt pricing 核心 |
| LIGHT/HEAVY heuristic pricing | 关闭 | 先缩小正确性路径 |
| 完整访问记忆 | 开启（小实例） | 保证 elementary pricing |
| dynamic ng、arc elimination | 关闭 | 依赖现有单车场流程，后续单独适配 |
| RCC、rank-1 cuts | 关闭 | M1 非目标 |
| enumeration、HGS | 关闭 | M1 非目标 |
| L2B、BKF、strong branching | 关闭 | M1 只需基础候选选择 |
| two-stage node I/O | 关闭 | 阶段模型生命周期不同 |

DVRP 使用独立功能配置，不改变静态 CVRP/VRPTW 的编译期默认值。

## 11. 验证顺序

1. 验证客户释放、承诺任务、外部起点和实际距离等动态状态规则；
2. 用枚举器列出手工小实例全部可行路线，验证 RMP 最优值；
3. 对每个起点单独验证时间、容量和回场可行性；
4. 比较枚举 reduced cost 与 pricing 最负列；
5. 验证加列后的行系数和 reduced cost；
6. 构造分数 LP，验证左右子节点与枚举结果一致；
7. 完成一个静态多起点 BP 后，再接入已经测试过的动态状态更新器；
8. 最后运行原 CVRP/VRPTW 静态回归。

## 12. 实现顺序

```text
阶段数据契约
  -> 动态状态更新器与 StageProblem 构建器
  -> 小实例枚举器
  -> 多起点 RMP
  -> 逐起点 exact pricing
  -> 带 startKey 的 add-column
  -> root column generation
  -> 起点专属有向弧 branching
  -> 动态状态更新与事件循环
```

每一步只引入一个可验证行为，前一步测试未通过时不进入下一步。
