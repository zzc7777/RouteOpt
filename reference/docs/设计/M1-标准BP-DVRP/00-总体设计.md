## 1. 目标与非目标

M1 要形成以下最小闭环：

```text
DVRP 八字段实例
  -> 动态事件与车辆状态
  -> 多起点静态阶段问题
  -> 标准 Branch-and-Price
  -> 阶段整数路线
  -> 推进到下一事件
  -> 累计实际执行距离
```

M1 先保证 2--5 个客户的手工实例语义正确，不追求 Solomon 100 客户性能。现有 CVRP/VRPTW 入口和默认流程不得改变。

## 2. 总体分层

| 层 | 职责 | 输入 | 输出 |
| --- | --- | --- | --- |
| 输入层 | 读取八字段 TXT | 文件路径 | 静态客户与披露时间 |
| 动态层 | 推进事件、车辆和承诺任务 | 上一阶段路线、当前时间 | 当前阶段快照 |
| 阶段构建层 | 把快照翻译为静态多起点 VRPTW | 阶段快照 | `StageProblem` |
| 阶段 BP 层 | RMP、pricing、加列和分支 | `StageProblem` | `StageSolution` |
| 仿真控制层 | 循环求解并累计已执行距离 | 全局问题 | 最终 DVRP 结果与日志 |

动态层不直接操作 LP、bucket 或 `BbNode`；阶段 BP 层也不决定客户何时披露、车辆当前承诺是否完成。

```python
state = create_initial_state(problem_data)

for event_time in disclosure_events:
    state = advance_previous_plan(state, event_time)
    state = release_customers(state, event_time)
    stage_problem = build_stage_problem(state)
    stage_solution = solve_stage_by_branch_and_price(stage_problem)
    state = accept_new_plan(state, stage_solution)

return finish_and_report_actual_distance(state)
```

## 3. 模块之间的数据契约

### 3.1 `StageProblem`

一次阶段求解只接收当前时刻的不可变快照：

```text
currentTime       当前事件时间 tau
customers         本阶段必须覆盖的客户及其值数据；不暴露未来客户
originStart       不限车辆数量的原始起点
externalStarts    执行中车辆各自的专属外部起点
returnDepot       语义独立的共同返回节点
returnDeadline    最晚返场时间 H，来自车场行 DUE_DATE
fixedCostAfterTau 不参与路线选择、但需要报告的固定剩余成本
```

### 3.2 `StartSpec`

每个起点至少携带：

```text
startKey           阶段内稳定且唯一的起点标识
kind               ORIGIN 或 EXTERNAL
locationCustomerId 外部起点对应承诺客户；原始起点对应原车场
startTime         原始起点按允许的最早时刻 tau 发车；外部起点为 T^k
remainingCapacity 原始起点为 Q；外部起点为 R^k
```

外部起点位于承诺客户的逻辑副本，不把该承诺客户再次放入覆盖集合。共同返回节点必须和所有出发起点保持语义分离。
原始车场选中路线按允许的最早时刻发车，可以提前到达客户处等待；外部车辆按 v4 在 `T^k` 完成承诺后立即出发。刚好在事件时刻完成服务时，为同一辆车生成本阶段外部起点，保留已占用容量，先重优化，再于同一时刻出发。

### 3.3 `StageRoute` 与执行轨迹

现有 `SequenceInfo` 只有客户序列，无法区分多起点。已实现的 `StageRoute` 表达下游选中的路线：

```text
startKey          从哪个原始/外部起点出发
customerSequence 本阶段访问的客户序列
```

动态层独立生成 `RouteExecution`，保存真实 `travelCost`、访问时间轨迹及返场时间；避免下游提交任意推迟发车的轨迹。该执行信息进入阶段记录。

### 3.4 `StageSolution`

已实现结果包含 `stageId`、求解状态、选中路线和诊断消息；可优化成本、固定成本与规范时间轨迹由动态层存入阶段记录。BP 统计以后由阶段求解器提供，当前不存在。仿真层不从 LP 内部对象反推动态状态。
不可行、超时无可行解和超时已有可行解必须区分，不能只用一个成功标志覆盖全部状态。已确认超时即停止仿真，即使有可行整数解也不继续；保留已有解用于诊断，不能报告为证明不可行或仿真完成。

### 3.5 当前动态模块的文件与接入方案（已实现）

本功能已实现状态推进、阶段输入生成和结果接收，以手工路线测试；阶段 BP 后续接入。3个生产文件（2个 `.hpp`、1个 `.cpp`）集中在 `packages_dvrp/application/dvrp/src/dynamic/`：

| 相对路径 | 职责 |
| --- | --- |
| `include/dynamic_data.hpp` | 定义车辆状态、`DynamicState`、`StageProblem`、起点和阶段路线结果等纯数据类型 |
| `include/dynamic_controller.hpp` | 声明初始化、推进到指定时间、生成阶段问题和接收计划的方法 |
| `src/dynamic_controller.cpp` | 实现上述方法，包含事件排序、距离结算和外部起点生成，不调用 LP 或标签算法 |

另加 `test/dynamic_test.cpp` 并更新 DVRP CMake 注册测试；不把 `main.cpp` 改成已经支持完整 BP。现有 reader 接口保留，不新增 `problem_data.hpp`；概念上的基础数据继续来自 `info_vertex`、容量等输入。动态模块本身用手工结果测试接收边界，不管理solver计时；后续已完成的小实例对照另负责CPLEX时间参数，真实观测与模拟停止的区别见其模块说明。

稳定的数据边界为：

```text
reader 输出（控制器构造时复制；原变量不需延长寿命）
  -> DynamicController 持有并推进实际状态
  -> StageProblem（本阶段固定快照）
  -> StageSolver（后续）
       -> 编号和数组转换 -> 根 RMP / pricing 初始化
       -> LP 对偶值 + 当前节点分支限制 -> 定价与加列、搜索树
  -> StageSolution（带起点身份的整数路线；时间轨迹由动态层重算）
  -> DynamicController 校验并接续执行
```

动态控制器拥有实际状态和执行计划；阶段快照保存当时的客户与起点值，不能随下一事件改变。阶段求解器拥有其数组和 solver/tree 工作区，返回路线结果后不把内部对象交给动态层。仅转换输入不能消除原有单车场假设，RMP、标签起终点和加列仍须分别适配。

本模块按用户“完成动态的实现和测试”的指令实现并测试；不代表下游 BP 方案已批准。具体接口为：

```cpp
DynamicController(info_vertex, capacity, instanceName);
StageProblem buildStageProblem() const;
void acceptSolution(const StageSolution& solution);
std::optional<double> nextEventTime() const;
void advanceTo(double nextEventTime);
void finish();
DynamicState state() const;
```

控制器一次复制 reader 数据，不要求调用方延长外部引用寿命。初始时刻为 0；事件严格按披露时间去重排序，`advanceTo` 只能前进至下一事件，不能跳过尚未规划的请求。返回的状态、阶段和记录均为值快照。`StageProblem` 仅携带本阶段客户数据及起点坐标/时间/容量，不暴露未来客户；连续客户编号转换由pricing独立完成，动态层不暴露内部数组下标。

原始起点 `startKey=0`；外部起点使用车辆终身不变的正整数编号，与客户 ID 属于不同命名空间。共同返回节点是单独字段，不能用起点 key 代替。动态模块不建立 BP 节点或桶图编号；定价模块拥有自己的编号。

阶段解带有 `stageId`、状态和路线选择（`startKey + customerSequence`），不接受下游任意延迟发车的轨迹。动态层独立生成并校验规范时间轨迹、真实成本和覆盖约束，存入阶段记录；这细化了 3.3 节的逻辑路线对象。提交错误路线时保持原状态不变。超时结果只保存诊断、不执行；可行整数路线接收不等于证明最优。

例：`tau=100` 时车辆尚在前往 A，预计 130 完成服务，已载 40、A 需求 20、Q=100。阶段外部起点为 A、130、剩余 40；实际载货仍为 40。下游可返回该起点后续访问 B 的序列；控制器保留前往/服务 A 的原轨迹，只替换 A 之后的计划。

独立验收覆盖同刻事件、途中/等待/服务承诺、容量投影、固定返场、结束车辆不复用、跨事件距离分割、末次事件收尾、错误路线原子拒绝和模拟超时停止；详见 `test/dynamic_test.cpp`。生产入口本轮仍只读取，不声称可自动求解 DVRP。

## 4. 阶段 RMP 设计

令 `lambda[s,r]` 表示从起点 `s` 使用可行路线 `r` 的变量。

### 4.1 客户覆盖行

每个本阶段客户恰好服务一次：

$$
\sum_s\sum_{r\in\mathcal R_s} a_{ir}\lambda_{sr}=1.
$$

### 4.2 外部起点行

每个外部起点对应一辆已经在执行任务的具体车辆，因此恰好选择一条后续路线：

$$
\sum_{r\in\mathcal R_k}\lambda_{kr}=1.
$$

外部起点允许“直接返回共同车场”的空客户路线，以表达不再接新客户；该路线也必须满足最晚返场时间 `H`，不能无条件作为可行列加入。

### 4.3 原始起点

原始起点代表不限数量的待命车辆，不建立现有 RouteOpt 的车辆数行。原始起点普通路线必须至少访问一个客户，避免产生无意义的空路线变量。

### 4.4 根 RMP 与 Phase-I

已实现的根模型为每行建立一个人工变量，并可加入可行的外部起点直接返场列、各起点单客户列。采用两阶段法：Phase-I 最小化人工量；人工量为0后固定人工变量为0、恢复真实路线成本，并重新求解复核真实LP可行性。

这一实现替代此前高惩罚人工变量的草案，不改变 v4 的真实目标。人工量正不直接说明完整阶段不可行，必须配合完整可行性定价；人工量零也不说明已有整数方案。完整定价结束前，当前RMP成本不能直接用于BP节点下界剪枝。

具体状态、目标切换、Phase-I/II 对偶输出和文件边界统一见[RMP 接口](02-多起点RMP文件与接口.md)，本页不维护第二套细节。当前只提供根RMP能力，搜索树及子节点可行性恢复以后设计。

## 5. Pricing 设计

本节只保留上层边界；详细接口见[03-多起点定价文件与接口](03-多起点定价文件与接口.md)，已实现能力与验证记录见[定价模块说明](../../实现说明/DVRP多起点定价模块.md)。

- 用户要求提供普通无桶标签版和桶图标签版，以同一接口显式选择。两版共用资源传播、支配判据、rc与回溯，标签调度各自实现；无桶版不构建桶图，不以一个大桶替代。
- 两版共同逐起点、完整访问记忆、前向扩展；各起点独立使用自己的 `startTime`、`remainingCapacity`，统一到 `returnDepot`，不先做超级源点图。
- 桶图以RouteOpt源码为主，复制适配统一时间bin、bin内SCC、待扩展标签、桶内/跨桶支配、排序和前缀成本界；论文用于理解与校验，不另写通用Phi扩展图。暂不含双向扩展/拼接、动态ng；原先弧消除/jump arcs等非目标不扩大。此为原版前向骨架适配，不是完整原版性能配置。
- Phase-I真实路线优化成本权重为0，Phase-II为1；两者可行域一致。每个客户dual减一次，外部起点dual仅减在该起点路线，原始起点不减车辆数dual。
- 定价接收阶段和有效dual，返回带 `startKey` 的候选及完成状态；LP由RMP持有，正式反馈循环由已实现的根列生成控制器管理。
- 本次定价只覆盖无分支的根模型。RF/cuts改变可行后缀后须重新适配扩展、支配和终止证明，不能假设现在的接口已支持子节点。

## 6. Add-column 与列生命周期

pricing 输出不能再只是客户序列，而应输出带 `startKey` 的候选路线。加列模块据此：

1. 从指定起点计算首弧；
2. 从最后一个客户连接独立 `returnDepot`；
3. 填写客户覆盖行；
4. 仅对对应外部起点行填写系数 1；
5. 原始起点列不填写车辆数行；
6. 用真实 RMP 系数复核 reduced cost 后加入 Solver 和当前节点列池。

真实路线与其 Solver 列号必须显式对应，人工列单独管理。本次基础路线校验和稀疏加列放在 RMP 控制器中；后续有明确复杂度收益时再决定是否拆独立 `add_column`，不重复实现模型写入。

## 7. Branching 设计

2026-10-25，按用户授权完成两种策略：RF（同路线覆盖关系）和起点专属有向弧（保留方向及 `startKey`），各自支持普通/桶图。当前能力见[模块说明](../../实现说明/DVRP双策略分支与受限列生成模块.md)，[设计05](05-双策略分支与受限列生成文件与接口.md)保留稳定接口；仅到候选、累计限制与受限节点LP，完整搜索树和生产整数恢复待另行确认。

两种策略分别支持普通/桶图后端，共用 RMP、列生成及未来的搜索树管理，不建立四套独立 BP。RF 已确认以客户行和外部起点行作为元素，原始起点不新增车辆数行；有向弧还须覆盖起始、终止及外部直接返场连接。

分支限制与 `StageProblem` 分离，沿节点历史累计，同时作用于主问题允许列和定价。RF 的后续任务义务会影响标签支配，弧分支的安全扩展/支配也须验证。仅筛选定价输出不构成精确定价；人工变量不参与真实分支流量。

首批已确认实现候选统计、左右限制和受限子节点 LP，再接共同搜索树。无分数候选时的恢复依据、分支充分性、子节点恢复及下界见设计05；生产整数恢复留到搜索树模块，本次无候选不直接标成整数最优。本节只保留上层边界，不作为第二份实施计划。

## 8. 动态阶段与 Solver 生命周期

每个事件时刻都必须从新的 `StageProblem` 重建根 RMP、pricing 上下文和搜索树：

```text
事件 tau_1 的 BbNode / 列 / dual / 分支约束
    不得复用到
事件 tau_2 的阶段模型
```

原因是客户集合、外部起点数量、起点时间、剩余容量和主问题行都会变化。阶段内父子 `BbNode` 可以按 Branch-and-Price 正常继承状态；跨阶段禁止继承 Solver 模型。

## 11. 验证顺序

1. 验证客户释放、承诺任务、外部起点和实际距离等动态状态规则；
2. 用枚举器列出手工小实例全部可行路线，建立完整 LP 和整数 MIP 对照；这不是生产 RMP 或列生成；
3. 对每个起点单独验证时间、容量和回场可行性；
4. 在同一组对偶值下核对 pricing 的路线 reduced cost 和无负列结论；若接口承诺最负列，再比较最小值；
5. 验证加列后的行系数和 reduced cost；
6. 构造分数 LP，验证左右子节点与枚举结果一致；
7. 完成一个静态多起点 BP 后，再接入已经测试过的动态状态更新器；
8. 最后运行原 CVRP/VRPTW 静态回归。

## 12. 实现顺序

```text
阶段数据契约
  -> 动态状态更新器与 StageProblem 构建器
  -> 小实例完整路线枚举 + CPLEX LP/MIP 对照（已完成，仅测试入口）
  -> 多起点 RMP
  -> 逐起点 exact pricing
  -> 带 startKey 的 add-column
  -> root column generation
  -> RF / 起点专属有向弧的限制与受限节点列生成（已实现，见设计05）
  -> 两种策略共用的 BP 搜索树及整数对照（后续另行确认）
  -> 将阶段 BP 接入已有动态状态更新与事件循环
```

每一步只引入一个可验证行为，前一步测试未通过时不进入下一步。
