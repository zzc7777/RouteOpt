# DVRP 动态状态与事件推进功能需求（简版 V3）

> 状态：待用户确认。
>
> 模型依据：`reference/docs/模型和推导/DVRP 数学模型-v4.md`。
>
> 阅读建议：重点看第 4 节“核心规则”和第 9 节“待确认问题”，其余部分用于说明与 RouteOpt 的接入边界。

## 1. 一句话目标

在独立 DVRP 入口中，根据客户披露事件和车辆当前状态生成一个静态的多起点 VRPTW 阶段问题，交给 RouteOpt 求解，然后推进到下一事件，直至所有车辆返场。

## 2. 原有功能简述

RouteOpt 当前求解的是静态 CVRP/VRPTW：

```text
实例数据
  -> InitialController
  -> 单车场主问题
  -> 单车场 pricing
  -> 加列、割、分支
```

它默认：

- 所有路线都从节点 `0` 出发并返回节点 `0`；
- 路线列只保存客户序列，不保存起点身份；
- 求解过程中没有客户动态披露、当前承诺客户或车辆跨阶段状态。

Java reference 已实现动态外层，但其中“使用弧上插值位置作为外部起点”和“返场车辆重新使用”等行为与数学模型 v4 冲突，因此只能作为辅助参考，不能直接照搬。

## 3. 目标流程

```text
DVRP reader
  -> 静态问题数据
  -> 当前事件和车辆状态
  -> 构建阶段问题
  -> RouteOpt 阶段求解器
  -> 阶段路线
  -> 推进车辆状态和实际距离
  -> 下一披露事件
```

动态层与求解层分开：

- 动态层决定哪些客户可重新规划、车辆从哪里以及何时继续出发；
- RouteOpt 只负责求解当前阶段的静态多起点 VRPTW；
- 每个阶段使用新的阶段状态，不直接修改上一阶段的 solver 和分支节点。

## 4. 核心规则

### 4.1 事件顺序

事件时刻由初始规划时刻和所有客户的 `DISCLOSURE_TIME` 组成，相同时间只求解一次。

在事件时刻 `tau`：

1. 将上一阶段路线执行到 `tau`，结算实际行驶距离；
2. 先处理在 `tau` 及之前完成的客户服务；
3. 再释放 `DISCLOSURE_TIME <= tau` 的新客户；
4. 生成新的阶段问题并求解。

如果客户服务完成与新请求披露同时发生，先完成服务，再进行重优化。

### 4.2 待规划客户

阶段客户集合只包含同时满足以下条件的客户：

- 已经公开；
- 尚未完成服务；
- 不是任何车辆当前正在执行的承诺客户。

每个待规划客户必须在阶段解中被服务一次且仅一次。

### 4.3 当前承诺客户

车辆正在前往、等待或服务的当前目的客户不能被重新分配：

- 行驶中的车辆继续到达该客户；
- 提前到达的车辆继续等待；
- 服务中的车辆继续完成服务；
- 完成服务后，车辆才执行本次重优化得到的后续路线。

一条计划路线中位于当前目的客户之后的客户尚未承诺，下一事件发生时允许重新分配。

### 4.4 外部起点

每辆执行中车辆生成一个专属外部起点 `O^k`：

- 位置：当前承诺客户的位置，不是事件时刻的弧上插值位置；
- 开始时间 `T^k`：当前承诺客户的服务完成时间；
- 剩余容量 `R^k`：完成该客户后车辆的剩余容量；
- 路线要求：必须选择一条后续路线，但可以不再服务客户而直接返场。

弧上插值只用于实际距离统计、车辆位置日志和固定剩余成本计算，不允许车辆在途中改道。

### 4.5 原始车场和返场车辆

- 原始车场用一个共享起点 `O` 表示，待命车辆数量不受限制；
- TXT 中的 `NUMBER` 继续读取和报告，但不形成阶段车辆上限；
- 正在返场的车辆保持原返场路线，不参与重优化；
- 已经返场的车辆结束本作业期任务，不再重新出车；
- 原始出发节点 `O` 和共同返回节点 `n+1` 在逻辑上分开。

### 4.6 成本

单个阶段的计划成本为：

```text
不可调整的固定剩余成本 + 本阶段选择的后续路线成本
```

固定成本包括完成当前承诺任务的剩余行驶成本和返场中车辆的剩余返场成本。它不影响路线选择，可以不放入 solver objective，但必须记录。

不同阶段的完整计划成本不能直接相加。最终 DVRP 结果只累计各事件区间真正执行的行驶距离，避免重复计费。

## 5. 阶段求解器的输入输出

输入：

- 当前事件时间；
- 待规划客户；
- 一个不限车辆数的原始起点；
- 零个或多个车辆专属外部起点；
- 共同返回车场；
- 固定剩余成本。

输出：

- 每条选中路线的起点身份；
- 客户访问顺序和时间轨迹；
- 阶段路线成本与求解状态。

阶段主问题至少保证：

- 每个待规划客户恰好覆盖一次；
- 每个外部起点恰好选择一条路线；
- 原始车场不设置车辆数量约束。

## 6. 相对 RouteOpt 的改动边界

| 类型 | 内容 |
| --- | --- |
| 保留 | 公共 LP/MIP solver、距离计算、容量和时间窗资源、列生成基本机制 |
| 新增 | DVRP 状态快照、事件推进、阶段问题、带起点身份的路线包装对象 |
| 修改 | DVRP 适配层中的主问题、路线可行性、pricing 起点和回场边界 |
| 不修改 | 原 CVRP/VRPTW 入口、命令行、实例读取和默认求解流程 |
| 首期关闭 | cuts、branching、enumeration、HGS、two-stage 等尚未验证的单车场加速模块 |

## 7. 首期不实现

- 不读取 Java Excel 作为生产输入；
- 不修改静态 CVRP/VRPTW 自动识别 DVRP；
- 不一次性迁移所有割、分支和加速策略；
- 不允许通过已知上界或实例名称替代动态状态建模；
- 不追求大实例性能，先保证小实例语义正确。

## 8. 验收标准

- 同刻披露只触发一次求解，服务完成先于披露处理；
- 行驶、等待和服务中的承诺客户均不会被重新分配；
- 外部起点的位置、`T^k` 和 `R^k` 符合 v4；
- 外部车辆可以直接返场，返场中和已返场车辆不再参与规划；
- 原始车场路线数量不受 TXT `NUMBER` 限制；
- 小实例中客户覆盖、容量和时间窗全部正确；
- 跨阶段实际距离不重复累计；
- 原 CVRP/VRPTW 构建和静态算例结果不回退。

## 9. 待确认问题

当前只保留两个需要用户确认的业务边界：

1. 新请求披露与原始车场计划发车恰好同时发生时，是否接受“先披露并重优化，尚未离场的车辆不视为已承诺”？本需求建议接受。
2. 距离、旅行时间和时间窗边界的取整规则，后续是完全沿用 RouteOpt 当前 VRPTW 规则，还是需要对齐 Java benchmark？需要在实现前通过现有代码和实例再给出具体建议。

接口类、内部 ID、solver 生命周期和逐文件改动属于技术设计，由实现阶段根据 RouteOpt 架构和测试决定，不要求用户在需求阶段逐项审阅。

## 10. 确认后的下一步

需求确认后，先实现阶段数据对象和不依赖 CPLEX/Gurobi 的状态更新器，用 2--5 个客户的手工实例验证第 4 节规则；通过后再单独设计 RouteOpt 阶段求解适配。
