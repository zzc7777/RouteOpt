## 1. 一句话目标

实现事件管理、车辆状态推进、`StageProblem` 生成及阶段路线结果接收，先用手工路线验证；阶段 BP 求解器另行实现，再接成完整动态循环。

## 2. 原有功能简述

原 RouteOpt：读取实例 → `InitialController` 初始化数组 → 单车场 RMP/pricing → 加列和分支。

它默认节点 `0` 为唯一车场，路线列不保存起点身份，没有披露事件和跨阶段车辆状态。源码入口为 `packages/application/cvrp/src/main.cpp`，初始化和根模型分别在 `src/initial`、`src/node`。

当前 DVRP reader 位于独立的 `packages_dvrp/application/dvrp`，输出 `info_vertex`、容量等外部变量，尚无动态层。Java 的弧中改道与返场车辆复用不符合 v4，只作兼容部分参考。

## 3. 目标流程

```text
reader 数据 + 上一阶段执行计划
  -> 动态状态推进 -> StageProblem
  -> 阶段求解器（后续功能）-> StageSolution -> 动态层接收新计划
```

动态层决定客户和起点；下游阶段求解器负责编号/数组转换、根 RMP 和标签算法。每阶段生成独立快照，不修改上一阶段的记录或复用旧阶段的 solver 模型。

## 4. 核心规则

### 4.1 事件顺序

事件时刻由初始规划时刻和所有客户的 `DISCLOSURE_TIME` 组成，相同时间只求解一次。
服务完成等执行事件更新车辆状态，不单独触发重优化。按 v4 忽略计算及指令传输耗时。

在事件时刻 `tau`：

1. 将上一阶段路线执行到 `tau`，结算实际行驶距离；
2. 先处理在 `tau` 及之前完成的客户服务；
3. 再释放 `DISCLOSURE_TIME <= tau` 的新客户；
4. 生成新的阶段问题并求解。

若服务完成恰好在 `tau`，先完成该客户，但暂不执行旧计划中同刻的下一次出发；在该位置生成 `T^k = tau` 的外部起点，重优化后于同一时刻立即出发。若车辆已在 `tau` 之前离开，则保持新目的地的承诺。

### 4.2 待规划客户

阶段客户集合 = 已公开客户 − 已完成客户 − 当前承诺客户；每个阶段客户恰好服务一次。旧计划中排在当前承诺任务之后的客户可重新分配。未来披露信息不参与当前求解。

### 4.3 当前承诺客户

正在前往、等待或服务的目的客户不可转交或中断；到早了等到时间窗开启，服务完成后立即执行后续路线，无后续客户则立即返场。同刻事件按 4.1 处理。
时间窗限制的是服务开始时刻；原始车场的最早实际发车规则见 4.5。

### 4.4 外部起点

每辆执行中车辆（包括恰好在 `tau` 完成服务的车辆）生成一个专属外部起点 `O^k`：

- 位置：当前承诺客户的位置，不是事件时刻的弧上插值位置；
- 出发时间 `T^k`：当前承诺客户的服务完成时间，不能任意推迟；同刻完成时为 `tau`；
- 剩余容量 `R^k`：完成该客户后车辆的剩余容量；
- 路线要求：必须选择一条后续路线，但可以不再服务客户而直接返场。

弧上插值只用于实际距离统计、车辆位置日志和固定剩余成本计算，不允许车辆在途中改道。
外部起点需求和服务时间为零，仍对应原车辆，不新增车辆或重置容量。`R^k` 包含当前承诺客户取货后的占用，但生成快照不能提前修改实际载货量，也不能跨事件重复扣除该需求。

### 4.5 原始车场和返场车辆

- 原始车场用一个共享起点 `O` 表示，待命车辆数量不受限制；同刻披露先纳入本阶段规划，再按结果于允许的最早时刻 `tau` 发车，可以提前到达等待；尚未出发的车辆不生成外部起点；
- TXT 中的 `NUMBER` 继续读取和报告，但不形成阶段车辆上限；
- 正在返场的车辆保持原返场路线，不参与重优化；
- 已经返场的车辆结束本作业期任务，不再重新出车；
- 原始出发节点 `O` 和共同返回节点 `n+1` 在逻辑上分开。
- 所有启用车辆须在车场行 `DUE_DATE`（记为 `H`）之前或恰好在 `H` 返回；固定返场车辆同样受此限制。该规则已同步到 v4。

### 4.6 成本

单个阶段的计划成本为：

```text
不可调整的固定剩余成本 + 本阶段选择的后续路线成本
```

固定成本包括完成当前承诺任务的剩余行驶成本和返场中车辆的剩余返场成本。它不影响路线选择，可以不放入 solver objective，但必须记录。

不同阶段的完整计划成本不能直接相加。最终 DVRP 结果只累计各事件区间真正执行的行驶距离，避免重复计费。

数值口径已确认采用 RouteOpt VRPTW：距离按原 `transformCost` 截断到一位小数（带容差），旅行时间使用同一弧距离；可行性比较沿用原容差。弧中按匀速进度结算，不对每个区间再次取整；等待、服务不累计距离，披露时间不额外截断。

### 4.7 收尾与求解失败

- 当前无待规划客户时，外部车辆仍须安排直接返场；还有未来请求时继续事件循环。
- 最后一个披露事件后，执行剩余计划直到全部客户完成、全部启用车辆返场，结清最终距离。
- 阶段被证明不可行时停止并保存快照和原因；超时无可行整数解时停止并报告未完成，不能声称已证明不可行。
- 超时已有可行整数解时同样停止仿真，保留已有解和阶段信息，报告超时未完成；不得用旧计划或当前可行解继续冒充完成。这里的超时指求解计算时间，不是客户时间窗。

## 5. 阶段求解器的输入输出

| 方向 | 数据 |
| --- | --- |
| 动态层 → 阶段求解器 | 时间、待规划客户、原始起点、外部起点、共同返回节点及 `H`、固定剩余成本 |
| 阶段求解器 → 动态层 | 求解状态、每条选中路线的起点身份、客户顺序、可执行时间轨迹和成本 |

下游保证每个客户恰好覆盖一次、每个外部起点恰好选择一条路径；原始车场无车队数量约束。动态层接收的是整数路线结果，不接收 LP 分数解或标签对象。

## 7. 首期不实现

- 不读取 Java Excel 作为生产输入；
- 不修改静态 CVRP/VRPTW 自动识别 DVRP；
- 本功能不实现 BP；完整 M1 的基础分支和高级增强边界由里程碑管理；
- 不允许通过已知上界或实例名称替代动态状态建模；
- 不追求大实例性能，先保证小实例语义正确。

## 8. 验收标准

- 同刻披露只触发一次求解，服务完成先于披露处理；
- 行驶、等待和服务中的承诺客户均不会被重新分配；
- 外部起点的位置、`T^k` 和 `R^k` 符合 v4；
- 外部车辆可以直接返场，返场中和已返场车辆不再参与规划；
- 原始车场路线数量不受 TXT `NUMBER` 限制，按最早允许时刻发车，提前到达则等待；
- 小实例中客户覆盖、容量和时间窗全部正确；
- 跨阶段实际距离不重复累计；
- 同刻服务完成保留外部起点，检查返场上限、末次事件收尾及模拟失败状态；真实 solver 超时联动留到下游接入时验证；
- 原 CVRP/VRPTW 构建和静态算例结果不回退。

## 9. 确认状态与本步边界

两项未决业务选择已确认：原始车场先处理同刻披露再发车；求解超时即停止，即使已有可行整数解也不继续。

本步不接入 solver，不实现计算时限或中止求解；只约定结果状态并以手工结果测试接收边界。真实超时与仿真停止的联动在阶段求解器接入时实现和验收，不作为当前模块的前置阻塞。
