# DVRP 共同 BP 搜索树与整数恢复：流程与方法导读

> 状态：已完成（单阶段BP方法导读）
>
> 最后更新：2026-10-26
>
> 能力范围、命令和验证证据集中在[模块说明](DVRP共同BP搜索树与整数恢复模块.md)。这里按一次真实调用解释代码，不要求逐行阅读C++。

## 1. 先分清三个对象

| 对象 | 可以怎样理解 | 不负责什么 |
| --- | --- | --- |
| `StageProblem` | 当前阶段的一份只读题目：客户、各起点时间/剩余容量、返回点、固定成本 | 不管理分支，也不是标签 |
| `BBTController<BranchContext>` | 待办队列：哪些子问题还没解决，每个有怎样的分支限制和下界 | 不认识路线，不调用CPLEX |
| `DVRP_BpController` | 总调度者：调用节点CG，决定分支、剪枝、接受整数解或停止 | 不推进真实车辆，不累计动态实际距离 |

生产入口在 [bp_controller.cpp](../../../packages_dvrp/application/dvrp/src/branch_and_price/src/bp_controller.cpp)。原来的 `DVRP_RootCgController` 负责“求一个节点LP”；新增BP负责“反复安排多个节点直到得到阶段整数结果”。没有复制四套求解器。

## 2. 进入solve：创建本阶段自己的树

调用 `solve(stage, options)`，显式选择RF或专属有向弧，以及普通标签或桶图。`BpDetail::validateStage`检查有限数值、客户/起点身份、容量和时间资源；非法输入返回Error。

随后 `addRoot` 创建节点0，限制为空。初始路线成本下界为0，因为本模型行驶成本非负；此时没有整数见证，所以没有有限上界。

阶段、候选、整数见证、节点记录都是值对象；不会把上一阶段的Solver或旧分支历史塞进新树。默认总预算60秒，从solve开始计时，不是每个节点各给60秒。

## 3. 取下一个节点：为什么还保留active

[`BBTController::startNext`](../../../packages_dvrp/branching/bbt/include/bbt_controller.hpp)取有效下界最小的节点，同界取ID小者。它从待办队列移出，却仍作为active保存。

例如队列只剩一个下界30的节点：取出后立刻超时，不能说“队列空了，所以求完了”。active表示这个子问题仍未解决；返回结果的全局下界仍包含30。

如果已有合法路线成本40，而这个节点下界已达到40（按显式容差），可以直接剪枝。否则检查节点预算，调用节点CG。节点预算统计真正启动的CG次数，纯界剪枝不占一次。

## 4. 求节点LP：还是之前的两阶段列生成

实际调用是 `DVRP_RootCgController{}.solve(stage, node.payload, options)`。传入的payload就是完整累计 `BranchContext`，子节点会重新建自己的RMP和pricing。

内部仍然是：人工变量Phase-I找可行LP → 固定人工量为零 → Phase-II最小化路线成本 → LP/dual/pricing/加列循环。细节见[节点CG导读](DVRP根节点列生成流程与方法导读.md)。

BP读取三类结果：

- `LpInfeasible`：核对Phase-I证书后结束该分区。
- `LpConverged`：核对Phase-II、阶段/节点/限制/版本，才允许使用该数值下界。
- 超时、资源/迭代上限或错误：停止整次BP，当前节点仍未解决。不能把部分定价结果拿来剪枝。

`updateActiveBound`取继承下界与新有效下界的较大者。CG的RMP目标不直接充当下界；BP用的是CG经过完整定价修正的 `bound.lowerBound`。

## 5. 选候选与恢复：lambda不是派车方案

`selectCandidate`仍来自已有分支模块，读同一份LP与列快照。随后调用 [`recoverIntegerRoutes`](../../../packages_dvrp/application/dvrp/src/branch_and_price/src/integer_recovery.cpp)，先重新核对候选来源，防止上一节点或旧LP的候选被误用。

恢复先尝试选择lambda接近1的路线，但这仅是提案。若它漏客户、重覆盖或资源不可行，提案作废；不是把每个lambda四舍五入后直接派车。

有分数候选且恢复不成，正常进入分支。没有分数候选时，才尝试结构恢复：

### RF：相同覆盖块选一条完整路线

例如原始起点两条路线 `[3,8]`、`[8,3]`，各0.5。客户3、8总是一起，RF找不到分数客户对，但两条路线变量仍是分数。

恢复将它们归入覆盖块 `{客户3, 客户8}`，选其中成本最低的允许路线；相同成本按起点和序列确定性选择。其他块必须与此块不相交，整组还要覆盖全部约束行。

外部起点也属于覆盖块：`K42 → 空客户 → 返回` 的块是 `{外部起点42}`。不可以把起点身份丢掉、只按客户序列合并。

### 专属有向弧：去重已有完整序列

按 `(startKey, from, to)` 汇总全部正值列的有向连接，包括Source和Return。如果连接接近整数，检查这些正列是否能去重成完整路线集合。

它不从几条零散弧拼接一条新路线。最终选择仍来自现有正值完整列，并接受完整可行性校验；这样不会把客户环或方向错误误当作车辆路线。

两种恢复均保留所有严格正列，包括极小值。浮点尘埃让覆盖块交叠或连接不一致时，可以明确返回 `NumericalUnresolved`；不能偷偷删掉它们再说证明完成。

## 6. validateIntegerRoutes：真正接受上界的门槛

对候选完整方案重新计算：

1. 每个客户恰好一次，每个外部起点恰好一条路线；原始起点路线非空。
2. 每条路线使用自身起点的坐标、出发时间和剩余容量。
3. 用RouteOpt距离口径传播到达、等待、服务和立即离站时间；检查所有时间窗及共同返场期限。
4. 检查不重复客户和当前全部分支限制；重算行驶成本，不信任列缓存。
5. 最后只加一次 `fixedCostAfterTau`，保存为 `IntegerWitness`。

这一步不调用动态 `acceptSolution`，因此不会真的发车。合法见证只产生上界U；其来源节点与限制也一并保存。若校验耗尽剩余时间，已完成校验的见证保留，但状态仍为超时。

## 7. 决定关节点还是分支

如果当前节点有效下界已不可能改善全局整数上界，`closeActive(false)`关闭并保留终结界。如果还有分数候选且界未闭合，就调用 `makeChildren`，把新决定分别加入左右孩子。

`nextChildIds`分配不同ID；`replaceActive`在两个孩子全部放入队列后才清除父节点。如果第二个孩子建立时分配内存失败，撤销第一个孩子，父节点仍保留。孩子继承父下界，不继承父的“LP已收敛”状态。

若同一变量已分过却再次被选中，停止报错，避免无进展循环。若无候选且整数见证/有效界不足以结束，返回数值未解决，不擅自启用MIP或换策略。

## 8. 何时整个阶段算求完

树的 `globalLowerBound`共同考虑：待处理节点、active、容差结束的分区下界，以及当前上界。父节点分裂后由孩子替代，不永久保留更弱的父界。

为什么记录已结束分区？假设成本40的见证允许一个下界39.9999999的节点容差剪枝，不能在清空队列后把全局下界直接写成40。代码保留真实的小gap，再按配置容差报告最优。

只有有合法见证并且有效全局gap闭合才返回 `Optimal`；所有分区证明不可行且无见证才返回 `Infeasible`。中断、错误、恢复失败不是这两个状态。

返回值保存每个处理节点的父ID、深度、累计限制、CG状态、LP目标、有效界、候选、处理原因及迭代统计；不保留所有节点的Solver和完整列池。`remainingNodes`在全局界提前闭合时可以非零，不必为证明冗余地处理所有节点。

## 9. 串起来看：LP30怎样成为整数40

三个客户各需求1、容量2、同在距车场10的位置，客户间距离0：

- 根节点可用三条双客户路线各0.5，LP成本30；这不能执行。
- RF选择一个客户对，生成分开/一起子问题；有向弧选择方式不同，但也调用同一套树。
- 子节点重新列生成，产生合法的“两客户一路＋一客户一路”方案，成本40。
- 校验方案得到上界40，继续处理或剪掉可能优于40的其他分区。
- 全局保守下界闭合后，返回整数路线和Optimal。测试中的阶段固定成本为7时，总计划成本是47，不是把每个节点目标相加。

五客户例会进入多层搜索，两种策略可能有不同节点数；这不影响“最优成本必须一致”的验收标准。

## 10. 下游现在接到哪里

`toStageSolution(result)`只是值转换：Optimal必须有见证和闭合的界；超时区分有解/无解；其余预算或数值失败映射为动态层已有的Error，并保留详细BP状态在原结果中。

当前测试调用到这里结束。下一模块才负责 `buildStageProblem → BP.solve → acceptSolution → advanceTo/finish` 的自动事件循环与CLI。不能把本文件的阶段算法完成解读为已经运行了完整动态仿真。
