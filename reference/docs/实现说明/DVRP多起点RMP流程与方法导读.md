## 1. 先分清谁负责什么

可以把 `DVRP_RmpController` 理解为 Java 中“持有一个 LP 模型的对象”：它会检查并保存路线，调用 CPLEX 求连续解，但不会自己寻找新路线。

`StageProblem` 是输入数据，不会自动求解。未来的阶段 BP 控制器负责创建 RMP、调用 pricing、判断定价是否完成；根节点/搜索树尚未接入。动态控制器不能拿 RMP 的分数路线直接派车。

目前真正调用这些入口的是 [rmp_test.cpp](../../../packages_dvrp/application/dvrp/test/rmp/rmp_test.cpp)。公开声明见 [rmp_controller.hpp](../../../packages_dvrp/application/dvrp/src/node/include/rmp_controller.hpp)，内部辅助方法均在 [rmp_controller.cpp](../../../packages_dvrp/application/dvrp/src/node/src/rmp_controller.cpp)。

## 2. 构造：`DVRP_RmpController(stage, options)`

输入为当前阶段快照和单次 LP 时限。内部 `Impl::validateStage()` 检查客户/起点身份、有限数值、容量和时间规则，然后建立两张互相独立的映射。

例如客户 ID 为5、8，外部车辆 key为42：

| 输入对象 | LP行号 | 该行要求 |
| --- | --- | --- |
| 客户5 | 0 | 所有服务客户5的路线变量之和等于1 |
| 客户8 | 1 | 所有服务客户8的路线变量之和等于1 |
| 外部42 | 2 | 所有从外部42出发的路线变量之和等于1 |

原始起点 key0 不产生车辆数量行。即使客户 ID 和车辆 key 恰好相同，也属于不同映射。

构造函数复制 `stage`，通过内部 `ModelOwner` 创建独立 CPLEX 环境和模型。随后建立3条等式和3个人工变量，此时尚无真实路线，处于 `Feasibility`（Phase-I）。上层仍需调用 `solveLp()` 才会求解。

## 3. 初始路线：`addInitialRoutes()`

这个公开方法依次尝试：

1. 每个外部起点直接返场；
2. 原始起点和每个外部起点分别服务一个客户后返场。

内部 `Impl::evaluate()` 从该起点自己的位置、出发时间、剩余容量出发，传播到达/等待/服务/返场时间，并重新计算真实距离。它不修改 `StageProblem`，也不推进动态车辆。

候选路线不可行就跳过，但一个直接返场列不可行，并不代表所有访问客户后返场的路线都不可行；截断距离不保证三角不等式。外部起点行也不会因此被删除。

筛选通过的路线统一交给 `addRoutes()`。没有生成多客户初始路线，也没有调用标签算法。

## 4. 所有加列共用：`addRoutes(routes)`

输入只有起点 key 和有序客户序列，例如 `{42,{8,5}}`；没有调用方指定的目标系数。

实际顺序是：

1. 用 `evaluate()` 检查整批路线；未知客户、重复客户或不可行路线会报错，尚未改写 LP。
2. 按“起点＋有序客户序列”去重，给新路线分配稳定 ID；重复项返回已有 ID。
3. `rowIndices()` 找出覆盖的客户行，再为外部路线加入对应起点行，非零系数都是1。
4. 构造稀疏列，调用 `Solver::addVars()` 加入 LP。Phase-I 的真实列目标为0；Phase-II 的目标为重算距离。
5. 成功后保存真实列元数据，增加 `modelRevision`，使旧 LP 结果失效。

在这个例子中，`{42,{8,5}}` 覆盖客户5、客户8、外部42共3行；它与 `{0,{8,5}}`、`{42,{5,8}}` 都不是同一条列。

人工列不属于真实路线 ID。假如有3行，真实路线 ID0对应 solver列3，而非solver列0；该区别由 `RmpColumn::lpColumn` 保存，调用方不必自行推算。

## 5. 求当前 LP：`solveLp()`

此方法只优化当前已有列，既不生成新列，也不证明尚未生成的列不存在。

内部先清除上一次结果，再调用 `Solver::optimize()`。`RmpDetail::classifyLpStatus()` 区分最优、超时、错误；只有当前 LP 最优时，才进入 `Impl::readOptimal()`。

`readOptimal()` 从 solver 读取变量值、目标、dual 和 reduced cost，再独立核对：

- 各变量有限、非负，且满足等式隐含的上界；
- 客户和外部起点等式是否满足；
- 根据真实列重新算出的目标是否等于 solver 目标；
- reduced cost 是否与目标系数减去行 dual 一致；
- 当前列的对偶可行性、互补性以及原始/对偶目标是否一致。

任何数值复核失败都清空有效结果并使模型停止使用，不将有问题的 dual 交给 pricing。

Phase-I 返回的是人工量，不是行驶距离。Phase-II 才有 `routeCost` 和加一次固定成本后的 `totalPlannedCost`。人工变量全部为零，也不表示路线变量全部是整数。

## 6. 人工量为零后：`enterCostPhase()`

调用方发现当前 Phase-I 人工量为零后，可以请求切换。该方法只使用控制器内部保存的最新已验证结果，不接受调用方传入一个“人工量零”的声明。

它将人工变量上界设为0、人工目标设为0，恢复真实列的距离目标，将阶段设为 `Cost`，并清除旧结果。随后调用方必须再次 `solveLp()`，才能取得新目标和dual。

未求过LP、人工量仍正、已切换过、或上次求解之后又加了新列，都不能直接切换。若固定为零后出现数值不可行，按错误处理，不报告完整阶段不可行。

## 7. 一个完整的手算执行例子

以下位置都在一条直线上：原始/返回车场0，客户5位于2，客户8位于4，外部42位于3。所有起点时间10，容量2，客户需求各1，宽时间窗、零服务时间，固定成本为0。

| 上层操作 | 方法 | 本步可检查结果 |
| --- | --- | --- |
| 建立空真实列池 | 构造＋`solveLp()` | 3行、3个人工变量，人工总量3 |
| 加原始→5→返回 | `addRoutes()`＋`solveLp()` | 人工总量2 |
| 加外部42→返回 | 同上 | 人工总量1 |
| 加外部42→8→返回 | 同上 | 人工总量0；不再选直接返场列 |
| 开始优化距离 | `enterCostPhase()`＋`solveLp()` | 原始车辆服务5、外部车辆服务8，LP成本9 |
| 加外部42→8→5→返回 | `addRoutes()`＋`solveLp()` | 一条接续路线成本5，LP成本降至5 |

测试入口为 `rmp_test.cpp::phases()`。这组过程没有实际派车，也没有推进动态时间；它验证的是同一个阶段内部的模型变化。

## 8. 下游怎样使用 dual？

`RmpDuals` 携带客户 dual、外部起点 dual、`phase`、`stageId`、`modelRevision`。pricing 必须使用对应阶段的资源和对偶，不能沿用上次事件或上次加列前的结果。

Phase-I 中一条真实路线的目标系数为0，Phase-II才是距离。外部路线还要扣掉自己的外部起点dual；原始路线没有车队行dual。容量、时间窗和允许路线集合不随这两个目标阶段改变。

原RMP测试中的 `scanPricing()` 用枚举全集计算 reduced cost，反复调用加列和求解入口；它只是测试驱动，不是生产 pricing。 后续另有[双版本标签定价及方法导读](DVRP多起点定价流程与方法导读.md)，其RMP接线测试用真正pricing供列，完整枚举仅负责核对；生产根控制器仍未接入。人工量正且扫描全集仍无改善列时，测试才有资格与完整 LP 的不可行结论比较。

## 9. 诊断与使用边界

`inspectModel()` 回读实际 solver 系数、边界、目标和连续 LP 类型，供矩阵核对；它不是定价循环中的必需步骤。`columns()` 用于查看稳定 ID、原始路线和真实成本，不允许外部修改模型。

非法输入会在加列前被拒绝；写入中途 API 失败则模型失效，下一次必须重建。超时不给可用于定价证明的数据。无客户且无外部起点时解析返回空最优结果；有外部起点时仍必须为每辆车安排后续路线。

本模块没有子节点复制、RF限制、重新开启Phase-I或生产事件循环。不要把一次 `OptimalRmp` 当作阶段最优，也不要把分数结果传给 `DynamicController::acceptSolution()`。
