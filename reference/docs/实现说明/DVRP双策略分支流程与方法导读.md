# DVRP 双策略分支：流程与方法导读

> 状态：已完成（候选、限制与受限LP；无自动搜索树）
>
> 最后更新：2026-10-25
>
> 能力、构建和验证见[模块说明](DVRP双策略分支与受限列生成模块.md)。这里解释业务怎样对应到实际方法，不重复测试矩阵。

## 1. 先区分数据和执行者

`StageProblem` 是同一次重优化的客户、起点、容量和时间数据。分支不会改变它。

`BranchContext` 像Python的一个配置对象，保存“节点ID、所选策略、累计限制”。它不是求解器，也不保存车辆执行状态。每一侧各有一份副本。

真正执行的方法分布在已有RMP、pricing、CG中；新增分支模块负责解释限制及选择候选。没有再复制两套标签算法或主问题。

```text
调用者拿到父节点闭合LP
  → selectCandidate：统计RF共同覆盖量 / 专属有向弧流量
  → makeChildren：复制历史，分别附加0与1
  → solve(stage, leftContext, options)
  → solve(stage, rightContext, options)
```

最后两次调用现在由测试显式发起。没有自动递归、节点队列、全局上界或剪枝树；这些是下一模块。

## 2. 整理限制：normalizeBranches()

源码：[branching.cpp](../../../packages_dvrp/application/dvrp/src/branching/src/branching.cpp)。输入是阶段和调用者的上下文，输出一个规范化副本。

它检查客户/外部key是否存在，RF两端是否不同，弧是否有合法起点和方向，历史是否混用了策略。RF两个元素不分先后，因此排序；有向弧不能交换两端。完全重复的决定只保留一次。

例：`客户3与5一起`重复两次只留一条；同时出现“一起”和“分开”则两条都保留。后者不是语法错误，而是可能不可行的子问题，不能在整理数据时悄悄覆盖其中一条。

`Customer(3)` 和 `ExternalStart(3)` 是不同元素，分别代表客户行和车辆起点行。弧的 `Source` 和 `Return` 也不同，即使物理位置相同。

## 3. 怎样选候选：selectCandidate()

上游提供匹配的 `RmpLpResult` 和 `columns`，其中 `lambda[id]` 对应 `columns[id]`。调用者必须先确认CG的状态为 `LpConverged`；单独一个 `OptimalRmp` 不证明全部列已经生成。

方法先核对Phase-II、人工量、阶段/节点/dual版本、客户及外部行覆盖残差，再累计真实列流量：

- RF：一条路线同时覆盖两个元素，就把该列lambda加到这一对。
- 专属有向弧：为路线补上Source和Return，逐段记录 `(startKey, from, to)`，不同方向/起点不合并。

在容差外仍为分数的候选中选最接近0.5者，平局按稳定的类型/编号顺序。人工变量不参与计数，也不先把lambda舍入成整数。

例如 `[3,5]`、`[3,8]`、`[5,8]` 各取0.5：RF对 `(3,5)` 的值是0.5；原始起点有向弧 `3→5` 的值也是0.5，但两种分支的含义不同。

找不到分数候选时返回 `NoFractionalCandidate`。比如同一批客户的两种访问顺序各取0.5，RF共同覆盖量可以全为整数，路线变量仍是分数。当前方法不会因此输出整数最优，更不会派车。

## 4. 生成两侧：makeChildren()

它接收父上下文、候选结果及调用者分配的两个新节点ID。检查候选来源后，各复制一次父历史：左加0，右加1；再规范化并返回。

不会复制Solver、父LP、dual或标签。节点ID只用于本阶段身份核对；后续搜索树负责分配全树唯一ID。本方法只检查两子ID互异、非0且不同于父ID，不管理全局ID注册表。

RF左侧表示不能同路；右侧表示一起或都不出现。弧左侧只禁特定连接；右侧表示总流量为1，不是每一条路径都必须使用它。

## 5. 子节点怎样启动：RMP构造与addInitialRoutes()

源码：[rmp_controller.cpp](../../../packages_dvrp/application/dvrp/src/node/src/rmp_controller.cpp)。CG每次创建一个带该上下文的全新RMP。

客户等式、外部起点等式和每行人工变量保持原样。`addInitialRoutes()` 先检查直接返场/单客户路线的资源可行性，再用 `routeAllowed()` 过滤限制违规者。

RF绑定3、5时，单客户3和5不能加入；人工变量会暂时承担它们的覆盖。随后Phase-I pricing寻找同时含3、5的路线，人工量归零后才切换成本阶段。初始列少，不等于子问题不可行。

`addRoutes()` 对外部传入整批列做独立资源和分支检查。任何一条违规都拒绝整批，不先写入前半批，也不静默吞列造成CG空转。

## 6. RF怎样进入标签算法

源码：[pricing_controller.cpp](../../../packages_dvrp/application/dvrp/src/pricing/src/pricing_controller.cpp)，内部结构见 [pricing_internal.hpp](../../../packages_dvrp/application/dvrp/src/pricing/include/pricing_internal.hpp)。

`PreparedStage` 将业务客户ID转换为内部1..n；`Work` 对每个起点编译限制。外部元素在该起点内是真或假常量。所有RF相关客户组成 `rfMask`，标签仍用已有完整 `visited`，没有新增独立“RF标签类”。

实际调用分为四步：

1. `Work::extend()` 尝试加入下一客户。“分开”双方将同时出现时立即拒绝；“一起”暂时只含一方仍可扩展。
2. `Work::dominates()` 在原资源、rc、访问集合条件之外，要求两标签的 `visited & rfMask` 相同。
3. `Work::complete()` 尝试返场时检查所有“一起”是否同时出现/缺席；未完成绑定任务的路线不能结束。
4. `Work::result()` 回溯路线后，再调用完整路线校验，保证输出见证符合历史。

例：绑定3和5。到达8的标签A已访问 `{3,8}`，标签B已访问 `{3,5,8}`。即使A时间、载重和rc都更小，它还欠客户5，不能直接代替已经完成绑定的B，因此不允许这次支配。

## 7. 有向弧怎样进入标签算法

仍是同一组 `Work` 方法，但编译为禁止客户、禁用弧和客户的强制前驱/后继。没有给每个标签增加“已经过哪些强制弧”的历史。

以强制外部起点K的 `3→5` 为例：

- 其他起点不再允许服务3、5。
- K路线到3后，下一个节点必须是5；进入5的前驱必须是3。
- 不涉及3、5的其他路线仍能生成；K的直接返场列单独看也允许，但完整外部等式会使其在满足强制客户路线时取0。

为什么能这样做？客户3/5各覆盖一次，指定弧流量必须为1，所以“覆盖端点但未用该K弧”的列只能取0。它是原等式的推论，不是额外引入业务约束，完整证明见设计05。

强制原始 `Source→3` 只约束客户3必须为该路线首客户，不会强制每条原始路线都经过3。强制外部 `Source→Return` 则使那辆外部车仅可直接返场。

`arcAllowed(from,to)` 同时在客户扩展和最终返场调用。重复指定不同后继被记录为冲突，而不是最后一条覆盖前一条。所有保留前缀均满足局部连接限制，因此同起点/同当前客户的原支配条件仍可使用。

## 8. 普通版和桶图版是否另写

没有。`runPlain()` 和 `runBucket()` 仍调用共用的 `extend / dominates / complete`；桶图、SCC、跨桶检查的主循环未改。

桶图先描述原本可能的连接，分支只从中排除连接或标签。它是允许图的超集，不会因为未为每个分支重造一张更小图而漏路线。桶最小rc只作保守扫描筛选，最终支配仍需RF状态一致。

## 9. 回到列生成与下游

源码：[root_cg_controller.cpp](../../../packages_dvrp/application/dvrp/src/column_generation/src/root_cg_controller.cpp)。新 `solve(stage, context, options)` 共用旧循环：LP → 同版dual → 所有起点受限定价 → 加负列 → 再LP。

RMP、dual、pricing及数值界携带同一上下文，避免左右节点恰好版本号相同却串用结果。最终见证再次核对起点、客户、资源、成本和分支。

Phase-I人工量仍正时，只有完整受限定价和正数值下界才报告不可行；超时、标签预算不足、迭代上限和数值未闭合不冒充证明。无负列且成本界闭合后输出当前节点LP，不是阶段整数方案。

三客户容量2、每条非空路线成本20的测试中：父LP30；RF左右子LP均40。这里验证的是“候选—限制—重新生成列”的接线。下一步共同搜索树才会决定继续分支哪个节点、恢复整数见证、更新全局上下界及何时结束。
